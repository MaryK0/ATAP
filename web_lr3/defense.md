## 1. Что было сделано и когда

Говорить можно так:

> В ЛР2 мы спроектировали OpenAPI-контракт и проверяли его линтером и mock-сервером.
> В ЛР3 по этому контракту реализовали настоящий ASP.NET Core API с PostgreSQL.
> Перед основной реализацией агент сопоставил операции с существующим кодом и записал план.
> По замечаниям преподавателя уточнили простой вход/выход и асинхронную выгрузку CSV.
> Прежний частичный API был незавершённой попыткой той же ЛР3. После уточнения контекста
> оставили одну версию `/api/v1` и заменили черновую реализацию.
> Затем последовательно проверили сценарий аэропортов, вход/выход, CRUD, аналитику, отчёты,
> выгрузки и совместимость интерфейсов. Проверили обнаружение намеренно испорченного ответа.

Журналы итогового прогона и восстановления после нарушения записаны **11.11.2026**:
`TestResults/lr3/stages-run.log`, `mutation-failed.log`, `mutation-restored.log`.
План и решения: `docs/lr3-plan.md`, `AI_REVIEW.md`. Точных дат отдельных строк реализации

## 2. Запустить обычный проект для показа

Команды выполнять из корня `C:/ATAP`. Docker Desktop должен быть запущен для PostgreSQL и Redis.

```bash
make db-up
make db-migrate
make build
```

Перед миграцией дождаться готовности PostgreSQL. Миграция `db/add_api.sql` добавляет таблицу
заданий выгрузки в существующую БД. Если приложение уже обновлено, повторно готовить БД для
каждого показа не требуется.

В трёх отдельных терминалах:

```bash
make run-api       # Swagger: http://localhost:5080/swagger
make run-blazor    # GUI: http://localhost:5075
make run           # TUI
```

API и Blazor используют обычную БД проекта. TUI отправляет HTTP-запросы через
`ATAP.ApiClient` на `http://localhost:5080/api/v1/`.

Использовать существующую учётную запись администратора. В новой БД из актуального DDL —
`admin` / `Admin#2026`; для ранее созданной учётной записи использовать её действующий пароль.
Аэропорт выбрать из `GET /airports`, период — по данным своей БД, не больше 31 дня.
Число записей заранее не фиксируется. Даты и airportId в JSON ниже — примеры, их нужно
заменить выбранными значениями.

## 4. Основное задание — по каждому пункту

### Пункт 1. Реализовать спроектированное API

**Показать:** `GET /api/v1/airports?limit=1&offset=0` в Swagger.
Ожидается `200`, не больше одного элемента в items, total — число аэропортов в БД,
limit=1, offset=0. Затем запросить аэропорт по id из ответа → `200`, заведомо
отсутствующий id → `404`, limit=0 → `400`.

Открыть последовательно:

1. `ATAP.Api/Controllers/CatalogController.cs`, методы Airports/Airport.
2. `ATAP.BusinessLogic/Domain/PlatformService.cs`, AirportsAsync/AirportAsync.
3. `ATAP.BusinessLogic/Domain/IPlatformRepository.cs`.
4. `ATAP.DataAccess/Repositories/PostgresPlatformRepository.cs`, AirportsAsync и PageAsync.
5. `ATAP.Api/Dtos/ApiDtos.cs`, преобразование ToApi для Airport.

**Сказать:**

> Контроллер принимает параметры HTTP-запроса и вызывает сервис. Сервис проверяет правила
> и обращается к интерфейсу Repository. Реализация Repository выполняет параметризованный SQL.
> Строка БД преобразуется в доменную модель, затем в API DTO и JSON. Здесь проходит весь
> сценарий от HTTP до реальных данных и обратно. Реализованы все 25 операций контракта.
> Генератор серверного каркаса не использовался: код написан с помощью агента и проверен тестами.

### Пункт 2. Подключить Swagger для документирования

### Пункт 3. Полнофункциональный Swagger UI

Нажать Try it out → Execute у публичного запроса. Показать Request URL, код, Response body и заголовки.

> Execute отправляет настоящий HTTP-запрос на сервер. Раздел Example Value — пример из
> документации, а Server response после Execute — фактический ответ реализации.

Продолжить в том же Swagger:

1. Без Authorize выполнить `GET /api/v1/reports` → `401`.
2. Выполнить `POST /api/v1/login`:

   ```json
   {"username":"admin","password":"Admin#2026"}
   ```

   Ожидается `201`, accessToken, tokenType=Bearer, expiresIn и пользователь.
3. Скопировать **только значение accessToken** в Authorize. Swagger добавляет Bearer автоматически.
4. `GET /api/v1/reports` → `200`.
5. Под admin создать временного пользователя через `POST /api/v1/users`:

   ```json
   {"username":"defense_user_1","email":"defense_user_1@example.com","password":"Example#2026","role":"analyst"}
   ```

   Ожидается `201`, Location и id. Записать возвращённый id; не подставлять заранее придуманный.
   При повторной репетиции взять новое имя/email либо удалить своего прежнего временного пользователя.
6. `GET /users/{id}` → `200`.
7. `PUT /users/{id}` с полным профилем:

   ```json
   {"username":"defense_user_1","email":"defense_user_1_put@example.com","role":"analyst"}
   ```

8. `PATCH /users/{id}`, Content-Type **application/merge-patch+json**:

   ```json
   {"email":"defense_user_1_patch@example.com"}
   ```

   Показать `200`: email изменился, username и role сохранились.
9. `DELETE /users/{id}` → `204`, повторный GET → `404`.

> Это полный CRUD пользователя. PUT заменяет редактируемый профиль, PATCH меняет переданные
> поля. Пароль и его хэш в ответах не возвращаются. За уникальностью следят сервис/БД,
> конфликт возвращается как 409. Пустой PATCH или недопустимые данные дают 400.

### Пункт 4. Чистая архитектура, Repository и три модели

**Показать три разные модели одного аэропорта:**

| Модель | Где | Назначение |
|---|---|---|
| AirportRow | `ATAP.DataAccess/Models/PlatformRows.cs` | Поля строки БД, чтение и преобразование данных хранения |
| Airport | `ATAP.BusinessLogic/Domain/Models.cs` | Доменная модель, независимая от HTTP и Npgsql |
| AirportResponse | `ATAP.Api/Dtos/AirportDtos.cs` | Внешняя структура ответа, согласованная с OpenAPI |

Показать `IPlatformRepository` в ядре и его реализацию PostgresPlatformRepository в DataAccess.
В Program.cs показать связывание интерфейса с реализацией через DI.

> Repository отделяет правила приложения от способа хранения. Контроллер не содержит SQL,
> домен не зависит от ASP.NET Core или PostgreSQL. API использует контроллерный подход
> ASP.NET Core MVC: запрос DTO → контроллер → сервис → результат DTO. Отдельный ViewModel
> для API не требуется; существующий Blazor использует ViewModel.

**Точное ограничение:** разделение Row/Domain/DTO выполнено в новом API. В legacy Blazor
AnalyticsViewModel и SavedReportViewModel ещё имеют прямые зависимости от Repository.
Не утверждать, что весь старый GUI уже приведён к цепочке View → ViewModel → Service → Repository.
Сохранение прежнего GUI и его перенос на API — отдельные вопросы; бонус переноса не выполнялся.

## 5. Замечание преподавателя: асинхронная выгрузка

В Swagger под analyst выполнить `POST /api/v1/exports`:

```json
{"airportId":1,"dateFrom":"2026-06-10","dateTo":"2026-06-10"}
```

1. Показать `202 Accepted`, id задания, заголовки Location и Retry-After.
2. Подставить id в `GET /exports/{exportId}`. HTTP-код — `200`, состояние — в поле status.
3. Дождаться completed; скачать `GET /exports/{exportId}/file`, Accept: text/csv.
4. Показать Content-Type, Content-Disposition и файл с данными за выбранный период.

> Запрос принимается быстро, файл формирует фоновый ExportWorker. Задание и результат
> сохраняются в PostgreSQL в dds.report_exports. Клиент периодически опрашивает состояние:
> queued, running, completed либо failed. Это polling, отдельный WebSocket не нужен.
> 202 означает «принято в обработку», а готовность показывает completed.
> Сохранённый отчёт хранит параметры, а задание выгрузки — состояние и конкретный CSV.

На маленьком наборе файл может быть готов уже при первом GET — это допустимо.
Показать `ExportWorker.cs`, `PostgresExportRepository.cs` и DDL `db/add_api.sql`.
Неготовый файл возвращает 409; чужое задание скрывается как 404. Эти случаи не нужно
создавать искусственной задержкой во время защиты.

### 4. Подтвердить соответствие контракту на реальном API

Для запуска уже настроенных автоматических проверок:

```bash
make test-lr3-stages
```

Команда сама использует тестовую инфраструктуру с фиксированными данными. Это способ
выполнения тестов, а не отдельный результат лабораторной и не подготовка ручной демонстрации.
На обычную БД этот набор не направлять: в нём проверяются конкретные значения из тестового SQL.
Показать 25/25 operationId и PASS. Количество HTTP-запросов может немного отличаться из-за polling.
Схемы проверяются на реальном ASP.NET Core API с БД, без Prism и без Prefer-заголовков.

Затем продемонстрировать обнаружение нарушения:

```bash
make api-mutation
```

> Скрипт временно добавляет JsonIgnore к Icao24 DTO воздушного судна. Реальный сервер
> перестаёт возвращать обязательное icao24. Контрактный тест падает, затем скрипт
> восстанавливает исходный DTO, повторно собирает сервер и получает успешный прогон.
> Схема и ожидаемые результаты для прохождения теста не ослабляются.

Открыть `TestResults/lr3/mutation-failed.log` и найти:

```text
listAircraft: data/items/0 must have required property 'icao24'
```

Затем показать PASS в `mutation-restored.log` и отсутствие JsonIgnore у Icao24 в текущем
`ATAP.Api/Dtos/ApiDtos.cs`. Скрипт пересобирает сервер на отдельных стендах; на это нужно время.
Не редактировать DTO параллельно с его работой. Если время защиты ограничено, заранее
прогнать команду и показать сохранённые логи вместе со скриптом.

## 7. Бонусы

**Бонус 1 — реализован.** Под analyst `GET /users` → `403`; без токена защищённый запрос → `401`.
После `POST /logout` повторный защищённый запрос с тем же токеном → `401`.

> Аутентификация определяет пользователя по токену. Авторизация проверяет его роль
> и принадлежность ресурса. JWT подписан HS256; Bearer — способ его передачи.
> Проверяются подпись, срок, издатель и получатель токена. Для немедленного выхода
> хранится реестр активных сессий; актуальная роль читается из БД.
> Пароли хэшируются PBKDF2 с солью. Реестр сессий пока хранится в памяти одного процесса.

**Бонус 2 — не выполнялся.** Blazor не переведён на HTTP API; он сохранён работающим через
прежние зависимости. Перенос TUI выполнен как обязательное требование. Не выдавать
сам факт работы Blazor рядом с API за выполнение бонуса переноса GUI.

10. logout → 401, бонус 1; пояснить отсутствие бонуса 2 и второй версии API.

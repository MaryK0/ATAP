# Асинхронная выгрузка аналитики

Актуальное описание единственного API `/api/v1` —
[`web_lr2/openapi.yaml`](../web_lr2/openapi.yaml). Контракт обновлён перед реализацией ЛР3.

Сохранённый отчёт (`reports`) хранит имя, аэропорт и период. Задание выгрузки (`exports`)
описывает конкретное формирование файла и его состояние. Это разные ресурсы.
Для выгрузки сохранённого отчёта клиент передаёт его аэропорт и период в `POST /api/v1/exports`.

## Последовательность запросов

Все запросы требуют `Authorization: Bearer <token>`.

1. `POST /api/v1/exports` с JSON-параметрами `airportId`, `dateFrom`, `dateTo`.
   Сервер проверяет параметры до постановки задания. Неверный период — `400`.
   При успехе — `202 Accepted`, описание задания, `Location` с адресом проверки
   и `Retry-After` с рекомендуемой паузой в секундах. `202` не означает готовность файла.
2. `GET /api/v1/exports/{exportId}` возвращает `200 OK` и состояние задания:
   `queued` (в очереди), `running` (выполняется), `completed` (готово), `failed` (ошибка).
   Для queued/running клиент повторяет GET с паузой из `Retry-After`.
3. При `completed` поле `downloadUrl` содержит адрес файла, `error` равно null.
   Клиент выполняет `GET /api/v1/exports/{exportId}/file` и получает `200` и `text/csv`.
4. При `failed` поле `error` содержит описание ошибки, `downloadUrl` равно null.
   Клиент прекращает опрос и показывает ошибку. В queued/running оба поля равны null.

`completed` и `failed` — конечные состояния. Проверка успешно прочитанного состояния
возвращает `200`, даже если само задание завершилось ошибкой: результат формирования
описывается полем `status`.

Попытка скачать ещё не готовый либо не сформированный из-за ошибки файл — `409`.
Несуществующее или чужое задание — `404`; отсутствие действительного токена — `401`.
Ссылка на файл не заменяет авторизацию. Повторный POST создаёт новое задание;
автоматически повторять его после сетевой ошибки без учёта этого нельзя.

## Почему это подходит ATAP

Это распространённый подход **Asynchronous Request-Reply с polling**:
[Microsoft Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply).
Код `202` означает принятие запроса на обработку, а не её завершение:
[RFC 9110, §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3).

Формирование CSV может занимать больше времени, чем чтение страницы аналитики.
Клиент получает короткий ответ и может продолжить работу, пока готовится файл.
На маленьких демонстрационных данных выигрыш по времени может быть незаметен;
это способ взаимодействия для потенциально длительной операции, а не обещание ускорить SQL.

Опрос состояния использует обычный REST API. SSE, WebSocket и webhook не нужны:
мгновенное уведомление не требуется, а опрос работает в Swagger UI, TUI и браузере.
В Swagger UI последовательные GET выполняются вручную, в клиенте их можно автоматизировать.
Статус `completed` со ссылкой выбран вместо перенаправления `303`, чтобы клиент
всегда получал описание задания в одном формате. Оба варианта встречаются на практике.

Существующее чтение аналитики `GET /congestion` и его CSV-представление сохраняются
для совместимости. Новый сценарий фоновой выгрузки использует `exports`.

Проверка схем и примеров подтверждает описание контракта. Фактическую фоновую обработку
и соответствие реального сервера этому описанию нужно проверить при завершении ЛР3.

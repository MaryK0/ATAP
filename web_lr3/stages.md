# WebLab#3 — этапы работы с агентом

Итоговая схема согласована автором: один API `/api/v1`, простой login/logout с JWT,
контракт — `web_lr2/openapi.yaml`. Прежний API был черновой попыткой этой же лабораторной,
а Blazor обращался к сервисам напрямую. Черновик заменён полной реализацией.

К моменту просьбы работать по этапам основная реализация уже существовала. Поэтому
ниже описана последовательная проверка и завершение частей, без заявления, что весь
код заново написан именно в таком порядке.

## 1. Один сценарий от HTTP до БД и обратно

`GET /api/v1/airports?limit=1&offset=0`

1. `CatalogController.Airports` получает параметры HTTP-запроса.
2. `PlatformService.AirportsAsync` проверяет пагинацию и вызывает `IPlatformRepository`.
3. `PostgresPlatformRepository.AirportsAsync` выполняет параметризованные SQL-запросы.
4. Модель БД `AirportRow` преобразуется в доменную `Airport`.
5. Контроллер преобразует доменную модель в API DTO `AirportResponse`.
6. Клиент получает `200`, JSON страницы с `items`, `total`, `limit`, `offset`.

На детерминированной тестовой БД проверяются: одна запись из трёх аэропортов, чтение
аэропорта 1, `404` для отсутствующего аэропорта и `400` для limit=0. Схемы реальных
ответов проверяются Ajv по OpenAPI. Это не mock-сервер.

Отдельный режим проверки — `ATAP_API_STAGE=airports`; результат — `stage-1-airports.log`.

## 2. Вход, текущая сессия, выход

`POST /login` → `GET /reports` → `POST /logout` → повторный `GET /reports`.
Ожидаются `201`, `200`, `204`, `401`. Данные пользователя возвращаются при входе.
Дополнительно проверяются неверный пароль,
лишнее поле запроса и защищённый запрос без токена.
Токен — подписанный HS256 JWT. Проверяются подпись, issuer, audience, срок и активность
сессии; роль читается из БД. Logout немедленно отзывает сессию по jti.

Отдельный режим — `ATAP_API_STAGE=auth`; результат — `stage-2-auth.log`.

## 3. Пользователи и остальные операции чтения

Регистрация и полный CRUD пользователя, PUT, PATCH только email без изменения других
полей, пустой PATCH, null, короткий пароль, неправильный Content-Type, конфликты и права.
Затем — суда, рейсы и позиции, включая отсутствие сущности и отказ без входа.

## 4. Аналитика и сохранённые отчёты

JSON/CSV, пагинация и сводка, включительные даты и граница 31 дня, неподдерживаемый Accept.
Создание, список, чтение, повторная аналитика и удаление отчёта; чужой отчёт возвращает 404.

## 5. Фоновая выгрузка CSV

Создание задания (`202`, Location, Retry-After), опрос состояния, completed и скачивание
файла. Содержимое CSV сравнивается с прямой выгрузкой за тот же период. Чужое задание
и файл скрыты как 404. Интеграционный тест отдельно проверяет захват очереди,
восстановление истёкшей аренды, завершение completed/failed и владельца.

## 6. Совместимость, ревью и передача

Unit, integration, E2E, TUI через HTTP при работающем Blazor, HTTP-страницы GUI и Swagger.
Отдаваемый сервером YAML сравнивается с единственным исходным контрактом.
Намеренное нарушение ответа проверяется отдельной командой `make api-mutation`:
отсутствие обязательного icao24 должно уронить тест; затем файл восстанавливается.
Ручная демонстрация кнопок Blazor описана в `README.md` этой папки.

## Запуск

```bash
make test-lr3-stages
```

Команда поднимает одноразовый стенд, последовательно выполняет этапы 1, 2 и полный
набор проверок 3–6. После ошибки следующие этапы не запускаются; стенд удаляется.
Логи находятся в `TestResults/lr3/`. Состояние прогонов фиксируется в `AI_REVIEW.md`.

## Подтверждённые результаты

Этап 1 проверяет 4 запроса; этап 2 — вход, защищённый запрос, выход и отзыв токена.
После удаления GET текущей сессии контракт содержит 25 operationId. Число запросов
зависит от опросов фонового задания. В актуальном прогоне после удаления GET сессии прошли 109 unit-тестов,
42 интеграционных, 1 E2E и сценарий TUI при работающем Blazor.
Демонстрация отсутствующего обязательного icao24 обнаружила нарушение реального ответа;
после восстановления DTO повторный прогон успешен.
Ручные действия кнопками Blazor ещё нужно показать в браузере.
Журнал актуального прогона — `TestResults/lr3/no-session-run.log`: этап 2 — 16 запросов,
полный сценарий — 77 запросов и 25/25 операций. Удалённый маршрут отдельно проверен как 404.

# WebLab#3 — реализация REST API

Полный сценарий защиты по каждому пункту задания и ИИ-трека, с командами и текстом выступления:
[defense.md](defense.md).
Конкретные значения для входа и сохранения отчёта через TUI на обычной БД:
[tui-demo.md](tui-demo.md).

Единственный API `/api/v1` реализует контракт [`web_lr2/openapi.yaml`](../web_lr2/openapi.yaml): 25 операций.
Автор уточнил, что прежний частичный API был черновой попыткой этой же ЛР3, а Blazor
не использовал его. Поэтому черновая реализация заменена полной; второй версии API нет.
Вход и выход используют подписанный HS256 JWT в заголовке Authorization Bearer.
Swagger UI использует единственный YAML; спецификация не генерируется заново из контроллеров.

## Что сделано по заданию

| Требование | Реализация и доказательство |
|---|---|
| Реализация OpenAPI | `ATAP.Api/Controllers`: вход, пользователи, воздушные суда, рейсы, позиции, аэропорты, аналитика, отчёты, фоновые выгрузки |
| Swagger UI | `/swagger`: один контракт `/openapi/openapi.yaml`, схемы, Authorize и Execute |
| Чистая архитектура, Repository, три модели | `DataAccess/Models/*Row` → `BusinessLogic/Domain` → `Api/Dtos`; явные преобразования, интерфейсы `IPlatformRepository` и `IExportRepository` в ядре |
| Подключение API | Контроллер принимает запрос DTO, вызывает сервис и преобразует результат в DTO ответа (MVC). SQL находится в Repository |
| TUI через API | `ATAP.ConsoleUI` зависит от `ATAP.ApiClient`, не от DataAccess. Тот же HTTP-клиент используется в меню и проверке `--smoke` |
| Совместимость Blazor | Сохранены существующие сервисы и Repository; общий хэшер проверяет старые SHA-256 и новые PBKDF2-пароли |
| Один API | `/api/v1`; старые дубли контроллеров удалены, E2E обновлён под login/logout |
| Бонус 1 | Простой вход/выход, подписанный JWT, роли, отзыв при выходе/смене пароля, запрет чужих отчётов и выгрузок |
| Бонус 2 | Не выполнялся: перенос Blazor на API опционален; сохранён рабочий прежний способ доступа |

Сценарии и operationId: [`scenarios.md`](scenarios.md).

## Запуск для демонстрации

Нужны .NET SDK 8, Docker; для проверки контракта — Node.js 18+ и npm.
Команды Make удобнее запускать из Git Bash. Рабочая БД не используется контрактными тестами.

Из корня репозитория:

```bash
make db-up
make db-migrate
make build
```

Миграция добавляет `dds.report_exports` без удаления существующих таблиц.
Если в исходном демонстрационном seed остался открытый пароль admin123, миграция заменяет
только это точное значение на PBKDF2-хэш пароля `Admin#2026`. Другие пароли не перезаписываются.
В новой БД начальный пользователь — `admin` / `Admin#2026`.

В трёх отдельных терминалах:

```bash
make run-api       # http://localhost:5080/swagger
make run-blazor    # http://localhost:5075
make run          # интерактивный TUI, обращается к API v1
```

TUI по умолчанию использует `http://localhost:5080/api/v1/`.
Другой адрес задаётся переменной `ATAP_API_URL` или `Api:BaseUrl` в настройках ConsoleUI.
TUI больше не требует собственного подключения к PostgreSQL или настройки StorageBackend.

## Что показать преподавателю

1. Открыть контракт v1: пути, DTO, роли и ошибки. Показать пример трёх моделей:
   `AirportRow` в DataAccess, `Airport` в Domain и `AirportResponse` в API.
   Проследить `GET /api/v1/airports` через CatalogController → PlatformService → PostgresPlatformRepository.
2. Открыть Swagger UI. Без токена выполнить `GET /airports` и `GET /flights/current`.
   Защищённый `GET /reports` без токена возвращает `401`.
3. Выполнить `POST /login` с логином/паролем. Скопировать только `accessToken` в Authorize
   (Swagger добавит `Bearer`). Выполнить защищённые запросы.
4. Под admin создать временного пользователя, прочитать, изменить `PUT`, затем выполнить
   `PATCH` только с новым email. Показать, что username и role сохранились. Удалить
   временного пользователя и показать `404` при повторном чтении. Удаление admin даёт `403`.
5. Под analyst создать отчёт, показать список, повторное чтение аналитики и удаление.
6. Выполнить `POST /exports`, например:

   ```json
   {"airportId": 1, "dateFrom": "2026-06-10", "dateTo": "2026-06-10"}
   ```

   Показать `202`, `Location` и `Retry-After`, затем `GET /exports/{exportId}` и поле status.
   После completed выполнить `GET /exports/{exportId}/file` с Accept: text/csv.
   На маленьких данных работа может завершиться до первой проверки: completed сразу при GET допустим.
   Для текущих данных выбрать период и аэропорт, присутствующие в своей БД.
7. Оставив API работающим, открыть Blazor и TUI. Выполнить вход в обоих, открыть карту/аналитику.
   Сохранить отчёт в одном интерфейсе и обновить список в другом — они работают с одной PostgreSQL.
   В TUI выгрузка CSV уже проходит через фоновое задание API; в Blazor действует прежняя выгрузка.
8. Выполнить `POST /logout`. Повторный защищённый запрос с прежним токеном даёт `401`.
9. Показать автоматические проверки и демонстрацию обнаружения нарушения контракта.

## Воспроизводимые проверки

```bash
make api-lint      # Redocly: структура OpenAPI, ссылки и примеры по схемам
make api-test      # реальный API + PostgreSQL/Redis в отдельном одноразовом Docker-стенде
make api-mutation  # временное нарушение реального ответа, падение теста, восстановление и успех
make test-lr3         # контракт, unit, integration, E2E v1, TUI HTTP, страницы Blazor
make test-lr3-stages  # сначала аэропорты, затем вход/выход, затем остальные проверки
```

Для уже запущенного изолированного тестового API с данными `db/test/03_seed_test_data.sql`:

```bash
npm ci --prefix web_lr3
ATAP_TEST_API=http://localhost:5080 node web_lr3/contract-tests.mjs
```

Не направлять этот набор на произвольную рабочую БД: ожидаемые числа аэропортов, рейсов
и аналитики заданы тестовыми данными. Скрипт создаёт временных пользователей и отчёты.
Prism здесь не используется. Ajv проверяет реальные JSON-ответы по схемам OpenAPI,
assert проверяет коды, значения, заголовки и бизнес-результаты сценариев.
Количество запросов может меняться из-за числа опросов состояния выгрузки.

`scripts/test-api-local.sh` — запасной запуск API из локальной сборки, если NuGet недоступен
из Docker. Он запускается внутри стенда с `ATAP_STAND_SERVICES="postgres-test redis-test db-e2e"`.
Дополнительная проверка при остановленном Redis:

```bash
ATAP_CHECK_NO_REDIS=1 bash scripts/test-stand.sh with bash scripts/test-api-contract.sh
```

Остановка затрагивает только Redis одноразового стенда. Проверяются успешные ответы карты
и аналитики; замеры задержек здесь не выполняются.

Локальные артефакты: `TestResults/lr3/contract.log`, `full-run.log`, TRX по проектам,
`tui.log`, `blazor.log`, `mutation-failed.log`, `mutation-restored.log`.
Файл, отдаваемый Swagger UI, сравнивается с исходным YAML. После прогона стенд удаляется.

## Границы реализации

JWT действует один час. Проверяются подпись HS256, issuer, audience, nbf/exp и активность
сессии. Актуальная роль читается из БД, поэтому её изменение действует сразу.
Реестр активных jti — память одного процесса: перезапуск API завершает все сессии.
Серверное состояние нужно для немедленного logout и отзыва токенов при смене пароля;
полностью stateless-авторизация здесь не заявляется. Ключ для развёртывания задаётся
через Jwt__Key; значение appsettings предназначено для локальной разработки.
JWT подписан, а не зашифрован; внешние подключения требуют HTTPS.
Задания и результаты выгрузки хранятся в PostgreSQL; прерванные задания подхватываются
после истечения пятиминутной аренды. Автоматического удаления старых CSV пока нет.
Генерация ограничена двумя минутами; завершение с ошибкой сохраняется как failed.
Для больших промышленных выгрузок потребуются потоковая запись и политика хранения.

Проверка `test-lr3` подтверждает HTTP-доступность страниц Blazor и работу HTTP-адаптера TUI
при одновременно работающих серверах. Она не заменяет ручной показ кнопок Blazor в браузере.
Тесты покрывают все operationId и основные ошибки; это не полный перебор всех входных данных.

## 4. Ресурсы: почему именно они

| Ресурс | Смысл | Операции (`operationId`) |
|---|---|---|
| `sessions` | Вход и выход; данные пользователя возвращаются при входе | `login`, `logout` |
| `users` | Регистрация и администрирование учётных записей | `listUsers`, `createUser`, `getUser`, `replaceUser`, `updateUser`, `deleteUser` |
| `aircraft` | Постоянные характеристики воздушного судна | `listAircraft`, `getAircraft` |
| `flights` | Конкретные рейсы | `listFlights`, `getFlight` |
| `flights/current` | Снимок последних позиций для карты | `listCurrentFlights` |
| `flights/{flightId}/positions` | Исторические точки трека конкретного рейса | `listFlightPositions` |
| `airports` | Справочник аэропортов | `listAirports`, `getAirport` |
| `congestion` | Вычисленное представление загруженности за период | `getCongestion` |
| `reports` | Сохранённые параметры анализа | `listReports`, `createReport`, `getReport`, `deleteReport`, `getReportCongestion` |

Воздушное судно и рейс — разные сущности: один борт выполняет множество рейсов.
Текущий снимок и исторический трек имеют разное назначение и объём данных.
Сохранённый отчёт хранит имя, аэропорт и период, а не неизменяемую копию CSV.
`GET /reports/{reportId}/congestion` повторно получает аналитику по сохранённым параметрам.

Не каждой сущности нужен полный CRUD: пользователь не должен вручную создавать позиции или редактировать данные OpenSky.
Для них достаточно чтения; запись выполняется загрузкой данных за границей публичного API.
Обновление сохранённого отчёта не требуется утверждёнными сценариями: нужны создание, чтение и удаление.

## 5. Почему это ресурсный API

В URI указаны ресурсы, а действие задаёт HTTP-метод:

```http
GET /api/v1/users/14
PATCH /api/v1/users/14
DELETE /api/v1/users/14
```

Вход — `POST /login`, выход — `POST /logout`. Данные пользователя возвращаются при входе.
Выгрузка — получение представления аналитики через `GET` с `Accept: text/csv`.
Нет необходимости придумывать отдельные команды `/login`, `/deleteUser`, `/exportCsv`.

REST — архитектурный стиль, а не синоним JSON. В проекте есть разделение клиента и сервера,
адресуемые ресурсы, стандартные методы и коды, согласование представлений и условные запросы.
Для закрытого запроса клиент каждый раз передаёт токен и необходимые параметры.
Хранение данных пользователей само по себе не противоречит stateless: речь идёт о контексте взаимодействия,
а не о запрете базы данных. При этом использование JWT само по себе ещё не доказывает stateless.

Оговорка для строгого вопроса о REST: полноценный HATEOAS в текущих ответах не спроектирован —
нет системы гипермедийных ссылок и допустимых переходов; клиент знает адреса из OpenAPI.
`Location` не заменяет полноценную гипермедиа. Не следует утверждать, что реализованы все ограничения REST в строгом смысле.
Исходное описание REST: [Fielding, глава 5](https://ics.uci.edu/~fielding/pubs/dissertation/rest_arch_style.htm).

## 6. Как читать YAML

| Элемент | Что означает |
|---|---|
| `openapi: 3.1.0` | Версия формата OpenAPI |
| `info.version: 1.2.0` | Версия конкретного контракта ATAP; это не версия HTTP |
| `/api/v1/` | Мажорная версия интерфейса в адресах |
| `servers` | Базовый адрес сервера; для локальной разработки указан `http://localhost:5080` |
| `paths` | Адреса ресурсов и операции над ними |
| `operationId` | Уникальное имя операции для трассировки сценариев и будущей генерации клиента; в HTTP не передаётся |
| `parameters` | Path-, query- и header-параметры |
| `requestBody` | Схема и примеры тела запроса |
| `responses` | Возможные коды, заголовки, типы содержимого и тела ответов |
| `components` | Переиспользуемые схемы, параметры, ответы, заголовки и описание аутентификации |
| `$ref` | Ссылка на общий компонент вместо копирования |
| `required` в объектной схеме | Какие свойства обязаны присутствовать; само по себе не запрещает пустые строки |
| `minLength`, `maxLength`, `pattern` | Ограничения строк |
| `additionalProperties: false` | Неизвестные поля объекта запрещены |
| `readOnly` / `writeOnly` | Направление использования поля; это описание контракта, не автоматическая защита сервера |
| `allOf` | Данные должны удовлетворять всем перечисленным схемам; используется для страниц |
| `security` | Стандартное описание требования аутентификации |
| `x-roles` | Собственное расширение, документирующее роли; инструменты не обязаны автоматически его исполнять |

Пример схемы: у `UserCreate` обязательны логин, email и пароль. Роль необязательна, но задавать её вправе только admin.
У `User` нет ни пароля, ни хэша. У `Role` всего два значения: `analyst`, `admin`;
гость определяется отсутствием входа, отдельной записи в БД нет.

`security: []` означает публичную операцию. `bearerAuth: []` требует bearer-токен, но пустой массив здесь не означает
«нет защиты»: для HTTP bearer в нём не перечисляют OAuth scopes.
В `createUser` альтернативы `{}` и `bearerAuth: []` разрешают анонимный и аутентифицированный вызов.
Условие «гость не может передавать role» записано в описании: одной схемой тела права вызывающего не проверяются.

## 7. CRUD и PATCH на конкретном примере

| CRUD | HTTP | Операция |
|---|---|---|
| Create | `POST /api/v1/users` | `createUser` |
| Read | `GET /api/v1/users`, `GET /api/v1/users/14` | `listUsers`, `getUser` |
| Update | `PUT /api/v1/users/14` | `replaceUser` |
| Частичный Update | `PATCH /api/v1/users/14` | `updateUser` |
| Delete | `DELETE /api/v1/users/14` | `deleteUser` |

PUT заменяет полный набор редактируемых профильных полей: `username`, `email`, `role`.
ID и дата создания назначаются сервером. Пароль в эту форму представления не входит и меняется отдельно через PATCH.
Тело PUT с одной ролью нарушает схему обязательных полей.

```http
PATCH /api/v1/users/14 HTTP/1.1
Host: localhost:4010
Authorization: Bearer <token>
Content-Type: application/merge-patch+json
Accept: application/json

{"role":"admin"}
```

Меняется только роль; отсутствующие поля сохраняются. Для смены пароля: `{"password":"N3w#pass2026"}`.
`{}` запрещён через `minProperties: 1`. Неизвестные поля запрещены.
В JSON Merge Patch `null` означает удаление свойства, поэтому здесь `null` для обязательных профильных полей запрещён схемой.
Массив в Merge Patch заменяется целиком, а не редактируется по индексам.
JSON Patch — другой формат: массив операций `add`, `remove`, `replace`; в ATAP он не используется.
Основание: [RFC 7396](https://www.rfc-editor.org/rfc/rfc7396.html).

## 8. Аналитика, пагинация, доступ и ошибки

Пример запроса:

```http
GET /api/v1/congestion?airportId=4&dateFrom=2026-06-10&dateTo=2026-06-10&limit=50&offset=0
Authorization: Bearer <token>
Accept: application/json
```

Обе даты включены: одинаковые даты означают один календарный день. Период — не более 31 дня;
при включительных границах 1–31 января допустимо, 1 января–1 февраля уже нет.
Без `airportId` аналитика строится по всем аэропортам. Сохранение требует конкретного аэропорта.

JSON возвращает `items`, `total`, `limit`, `offset` и сводку `summary`.
`total` — число всех записей по фильтру, а не длина текущего `items`; счётчики также относятся ко всему периоду.
Например, `limit=50&offset=100` означает пропустить 100 записей и вернуть до 50 следующих.
Обычный предел `limit` — 1000, значение по умолчанию — 50; для аэропортов максимум увеличен до 10000.
Снимок карты возвращается целиком без пагинации и сужается фильтрами.

Для CSV тот же ресурс запрашивается с `Accept: text/csv` и отдаёт все записи периода без пагинации.
`Content-Disposition` предлагает имя скачиваемого файла. CSV описан строковой схемой:
линтер не проверяет тип каждой CSV-колонки так же строго, как JSON-объект.

Гостю доступны аэропорты и текущая карта. Аналитика, отчёты, справочник бортов, рейсы и исторические треки
требуют роли analyst/admin. Управление пользователями — admin; самостоятельная регистрация — исключение.
Чужой отчёт возвращает `404`, чтобы не раскрывать его существование.

Ошибки используют `application/problem+json`: `type`, `title`, `status`, при необходимости `detail`, `instance`, `errors`.
`errors` — расширение для ошибок отдельных полей. Обязательность `type/title/status` задаёт именно контракт ATAP,
а не универсальное требование ко всем Problem Details. Основание формата: [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html).

Проверки `dateFrom ≤ dateTo`, длительности периода, существования аэропорта и прав доступа описаны словами и ответами.
Они не становятся автоматически исполнимыми проверками JSON Schema. Их реализация относится к WebLab#3.

## 9. Как устроены автоматические проверки

`redocly.yaml` расширяет набор `recommended` и повышает проверки примеров до `error`:
`no-invalid-media-type-examples`, `no-invalid-parameter-examples`, `no-invalid-schema-examples`.
Дополнительно проверяются наличие и уникальность `operationId`, описания, ссылки, параметры путей и другие правила.
Комментарий о версионировании в конфигурации не равен отдельному правилу проверки префикса:
`no-http-verbs-in-paths` проверяет глаголы, а не `/api/v1/`. Фактические пути контракту соответствуют.

`mock-scenario.mjs` запускает Prism 5.16.0 по YAML на порту 4010, ждёт готовности,
делает запросы через Node `fetch`, проверяет ответы и останавливает сервер в `finally`.
При провале возвращает ненулевой код. Node нужен версии 18 или выше.

Сценарий аналитика: вход → аэропорты → аналитика без токена → JSON → CSV → неверный отчёт →
пример ошибки аэропорта → создание отчёта → список → повторная выгрузка → удаление → пример 404 → выход.

Сценарий администратора: вход → список → ошибки длины пароля → пример ошибки пароля → создание →
пример конфликта → чтение → PUT → неполный PUT → PATCH → пустой PATCH → null → короткий пароль →
неверный Content-Type → пример запрета удаления admin → удаление. Всего оба сценария содержат 30 проверок.

Нужно различать три вещи:

1. **Нарушение схемы запроса.** Пустое имя, пароль из 3/129 символов, неполный PUT, пустой PATCH,
   null, короткий пароль в PATCH проверяются Prism; скрипт проверяет код и заголовок `sl-violations`.
2. **Выбор документированного ответа.** Заголовок `Prefer: code=404` либо `Prefer: code=400, example=unknownAirport`
   просит Prism вернуть определённый пример. Это управление mock, а не проверка состояния БД.
3. **Действительная бизнес-логика.** Создание, хранение, уникальность логина, отзыв токена, права ролей и проверка периода
   должны проверяться на реальном API в WebLab#3. `x-roles` не превращает Prism в реализацию RBAC.

Mock не хранит созданных пользователей и отчётов, не обязан возвращать именно отправленные значения.
В сценарии пользователь после PUT/PATCH становится admin, затем mock позволяет DELETE: на реальном сервере
такой сценарий противоречил бы запрету удаления admin. Здесь проверяются независимые примеры операций.
Удаление с последующим принудительным `Prefer: code=404` не доказывает, что ресурс действительно удалён.
Скрипт, зависящий от `Prefer` и `sl-violations`, нельзя без доработки считать полноценным тестом реального API.

## 10. HTTP: методы и идемпотентность

HTTP — протокол прикладного уровня. REST использует его семантику, но не является отдельным протоколом.
В HTTP/1.1 запрос содержит стартовую строку, заголовки, пустую строку и необязательное тело;
ответ — строку статуса, заголовки и необязательное тело. В HTTP/2 и HTTP/3 передача организована кадрами.

| Метод | Назначение | Безопасный | Идемпотентный по определению |
|---|---|---|---|
| GET | Получить представление | Да | Да |
| HEAD | Метаданные как у GET, без содержимого ответа | Да | Да |
| POST | Обработка данных ресурсом; у нас создание | Нет | Не гарантируется |
| PUT | Создать или полностью заменить состояние по известному URI; ATAP здесь обновляет существующего пользователя | Нет | Да |
| PATCH | Применить частичные изменения | Нет | Не гарантируется; зависит от формата и операции |
| DELETE | Удалить связь URI с ресурсом | Нет | Да |
| OPTIONS | Получить сведения о возможностях взаимодействия | Да | Да |
| TRACE | Диагностическая петля запроса, обычно ограничена на серверах | Да | Да |
| CONNECT | Создать туннель | Нет | Не гарантируется |

Безопасность метода означает, что клиент не запрашивает изменение состояния; логирование GET допустимо.
Идемпотентность — одинаковый предполагаемый эффект одного и нескольких одинаковых запросов, а не одинаковый ответ.
Первый DELETE может вернуть `204`, второй `404`: ресурс остаётся удалённым.
После выхода повторный DELETE с отозванным токеном может вернуть `401`: сессия остаётся завершённой.
Повтор POST отчёта может создать дубль, поскольку имя отчёта не уникально и ключа идемпотентности нет.

PATCH `{"role":"admin"}` присваивает значение и по эффекту может быть идемпотентным;
PATCH с командой «увеличить на 1» — нет. Нельзя говорить, что любой PATCH всегда неидемпотентен.
GET с телом не используется: у такого содержимого нет общей определённой семантики, фильтры передаются в query.
Методы чувствительны к регистру; имена заголовков — нет.
Основание: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).

## 11. HTTP: коды и заголовки

| Код | Значение и пример |
|---|---|
| 200 | Успех с представлением: чтение, PUT/PATCH пользователя |
| 201 | Создан ресурс: пользователь, отчёт, сессия |
| 202 | Принято для обработки; завершение ещё не гарантировано; в текущем контракте не применяется |
| 204 | Успех без содержимого: удаление, выход |
| 304 | Условный GET: представление не изменилось; использовать сохранённое; содержимого нет |
| 400 | Неверные данные: поля, период, ссылка на аэропорт |
| 401 | Нужна действительная аутентификация; включает `WWW-Authenticate` |
| 403 | Запрос запрещён: недостаточно прав или нельзя удалить admin |
| 404 | Целевой ресурс не найден либо его наличие скрывается |
| 405 | Для ресурса не разрешён метод; ответ содержит `Allow` |
| 406 | Сервер не может предоставить приемлемый формат ответа по `Accept` |
| 409 | Конфликт с состоянием: заняты логин/email |
| 412 | Условие запроса не выполнено, например не совпал `If-Match`; в ATAP такое обновление пока не предусмотрено |
| 415 | Не поддерживается формат содержимого запроса по `Content-Type` |
| 422 | Синтаксис понятен, инструкции обработать нельзя; ATAP для ошибок данных согласованно использует 400 |
| 429 | Слишком много запросов; в текущем контракте не предусмотрен |
| 500 | Внутренняя ошибка сервера |
| 502 / 504 | Шлюз получил неверный ответ / не дождался вышестоящего сервера |
| 503 | Временная недоступность сервиса; для карты предусмотрен `Retry-After` |

Классы: 1xx — информационные, 2xx — успех, 3xx — перенаправления/условные ответы,
4xx — проблема запроса, 5xx — проблема сервера. Не все перечисленные выше коды заложены в ATAP:
таблица включает материал для устных вопросов.

| Заголовок | Назначение |
|---|---|
| Content-Type | Формат содержимого данного сообщения; в запросе PATCH — `application/merge-patch+json` |
| Accept | Какие форматы ответа принимает клиент; например `text/csv` |
| Authorization | Учётные данные; в ATAP — `Bearer <token>` |
| WWW-Authenticate | Указывает механизм аутентификации, нужен для 401 |
| Location | URI созданного ресурса для 201 или адрес перехода для перенаправления |
| ETag | Непрозрачный идентификатор версии представления |
| If-None-Match | Просьба вернуть содержимое, только если версия отличается; иначе для GET/HEAD — 304 |
| If-Match | Разрешить изменение только при совпадении версии; защита от потерянных обновлений, пока не заложена в ATAP |
| Cache-Control | Правила кэширования; у снимка карты показан `max-age=300` |
| Vary | Какие поля запроса влияют на выбор представления; учитывать `Accept` при кэшировании JSON/CSV |
| Content-Disposition | Предложенное имя скачиваемого файла |
| Retry-After | Через сколько секунд или после какой даты повторить запрос |
| Allow | Разрешённые методы ресурса; отличается от CORS-заголовка `Access-Control-Allow-Methods` |

Цикл карты: GET → `200` и ETag → повторный GET с `If-None-Match` → `304`, если версия та же.
`no-cache` разрешает хранить ответ, но требует перепроверки; `no-store` запрещает хранение.
Redis — серверный кэш данных, а HTTP-кэш — отдельный механизм взаимодействия с клиентом/посредниками.
Основание кэширования: [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html).

Почему `400` для неизвестного `airportId` у `/congestion`: сам целевой ресурс существует, неверен параметр.
У `GET /airports/99999` неизвестен уже целевой ресурс — `404`.
Почему удаление admin — `403`: операция запрещена бизнес-правилом.
Почему при самостоятельной регистрации может не быть `Location`: стандарт не требует этот заголовок для каждого 201;
в проекте ссылка на административное чтение возвращается только admin, а данные нового пользователя — в теле.

## 12. Ещё вопросы по семейству HTTP

**HTTP/1.1, HTTP/2, HTTP/3.** Общие методы и коды сохраняются. HTTP/1.1 использует текстовый формат сообщений;
HTTP/2 — бинарные кадры и несколько потоков в TCP-соединении, HPACK для заголовков;
HTTP/3 — QUIC поверх UDP, QPACK для заголовков. Потеря TCP-пакета может задерживать все потоки HTTP/2;
QUIC уменьшает такую зависимость между потоками. HTTP/2 при этом не становится UDP-протоколом.
Основания: [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html), [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html).

**HTTPS.** HTTP с защитой TLS: конфиденциальность, целостность и проверка подлинности сервера.
JWT не заменяет HTTPS: подпись токена не шифрует его содержимое и не защищает транспорт.
Bearer означает, что обладатель токена может его использовать. Подписанный JWT обычно читается без секретного ключа.

**CORS.** Браузерное правило доступа между origin, где origin — схема, хост и порт.
Для SPA с другого origin браузер может сначала отправить preflight OPTIONS с
`Origin`, `Access-Control-Request-Method`, `Access-Control-Request-Headers`.
Сервер отвечает разрешающими `Access-Control-Allow-*`. CORS не заменяет проверку прав и не ограничивает curl.
Для этого проекта настройка CORS отложена к реализации API/подключению SPA.

**Перенаправления.** 301/308 — постоянные, 302/307 — временные;
307/308 сохраняют метод и содержимое запроса, 301/302 допускают историческое превращение POST в GET;
303 ведёт к получению другого ресурса, обычно через GET.

**URI, path, query.** В `/api/v1/users/14` path выбирает конкретного пользователя.
В `?role=admin&limit=50` query задаёт фильтр и страницу. Fragment после `#` серверу в HTTP-запросе не передаётся.

## 13. Почему не нужны дополнительные протоколы

Карта обновляется раз в пять минут: достаточно GET и условных запросов.
SSE имел бы смысл для частых однонаправленных обновлений, WebSocket — для двустороннего обмена.
Чата или совместного управления в требованиях нет. Межсервисных RPC-вызовов для gRPC тоже нет.
Нет требования к доставке событий через брокер или webhook. Airflow самостоятельно загружает данные из OpenSky.
SignalR в Blazor обслуживает работу самого интерфейса и не означает, что внешнему публичному API нужен WebSocket-контракт.

## 15. Что учитывать перед сдачей

- YAML актуальнее отдельных исторических записей. В `scenarios.md` сценарий карты пока показывает только `bbox`,
  хотя в 1.2.0 уже есть `minAltitude`, `maxAltitude`, `originCountry`; это небольшая несогласованность таблицы.
- Изначально фильтры в README предназначались аналитику, но последующее решение автора разрешило их всем ролям
  для публичной карты (`AI_REVIEW.md`, раздел «Фильтры карты»). YAML отражает это решение.
- Пример `Location` у создания пользователя и ID в примере тела не согласованы между собой (`14` и `13`).
  Линтер проверяет схемы по отдельности и не замечает такую смысловую несогласованность.
- В ответе 304 сейчас нет описания ETag; для полноты контракта условного кэширования его стоит описать и там.
- В примере аналитики вход в 07:06 и выход в 07:08 сочетаются с длительностью 96 секунд.
  Проверка типов это пропускает; если длительность означает разность этих времён, пример требует согласования.
- Полноценная гипермедиа не описана. При строгом требовании HATEOAS это отдельный вопрос к контракту,
  который не решается успешным запуском линтера.
- Результаты unit/integration/E2E и покрытие не заменяют проверки WebLab#2. Здесь важно показать YAML,
  линтер, проверку примеров, mock, достаточность сценариев и историю содержательного изменения.
- Реализованный срез API, SHA-256 вместо PBKDF2 и незавершённые части Blazor относятся к реализации;
  не следует выдавать их за выполненную реализацию всего спроектированного контракта.

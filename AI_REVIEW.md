## WebLab#1 — проектные материалы

**Задача.** На основе существующего репозитория ATAP (README, диаграммы `web_lr1/diagrams/`,
исходный код) подготовить в .md кратко: цель, FR/NFR, use-case, ≥ 3 нелинейных BPMN, ≥ 3 сценария,
ER, стек, диаграмму БД, C4 L1–L3, черновые экраны, ≥ 2 ADR. Перед этим — разбор проекта: карта
компонентов, ограничений и пробелов; факты отдельно от предположений; открытые вопросы с вариантами.

**Инструмент/модель.** Claude Code (Claude Opus 5.5), интерактивная сессия в VS Code. Первая версия
комплекта (v1.0, отдельный `web_lr1/WebLab1.md` + `web_lr1/adr/`) была сделана ранее и заменена.

**Результат.** [README.md](README.md) — единственный документ: все пункты задания, диаграммы —
PNG из `web_lr1/diagrams/` (исходники `.puml` рядом), ADR — в README §12. Разбор проекта и
открытые вопросы с ответами — ниже в этом разделе.

**Проверка.** Документация, поэтому формальный «запуск» неприменим. Проверено так: каждое
утверждение о коде сверено с файлом и строкой (таблицы ниже); все ссылки на изображения в README
указывают на существующие файлы.

### Решения

**Принято пользователем.** Комплект переписан заново. Диаграммы не дублируются: остаются только
PNG/puml, на которые ссылается README; mermaid-копии, отдельный `WebLab1.md`, файлы `adr/` и
`bpmn/*.mmd` удалены. ADR помещены в README.

**Отклонено пользователем.** Правки `use_case.puml` и `c4/l2.puml`: диаграммы не перерисовываются;
граница Airflow задана в README §2, а L2 по решению Q-3 показывает целевую архитектуру.

**Принято пользователем.** README — описание продукта: из него убраны ссылки на другие
лабораторные, временные пометки и примечания о расхождениях с кодом (они остаются в G-1…G-12),
разделы вне задания (открытые вопросы — сюда, материалы ЛР6/ЛР7 — в `LR6_LR7.md`).
Псевдографика экранов заменена скриншотами реального приложения, диаграммы последовательностей
убраны как не требуемые заданием.

**Исправлено после проверки.** В первой версии разбора ИИ сам выбрал ответы на открытые вопросы
(экран мониторинга, единицы радиуса, C4 L2, стек) — это противоречило заданию («не придумывай
ответ»). Выбранные ответы убраны, вопросы вынесены с вариантами в раздел «Открытые вопросы» выше.

### Решения по разбору

- **Р-1. Уточнено:** AGENTS.md и TESTING.md переведены на README как единственный документ
  комплекта; убраны ссылки на несуществующие файлы и разделы; словарь (`analysis_radius`, роли) и
  примечание про `StorageBackend` приведены к фактам и открытым вопросам. *Почему:* AGENTS.md —
  контекст для агента в WebLab#2/#7; битые ссылки и неверные факты в нём ведут к ошибкам генерации.
- **Р-2. Принято:** при расхождении BPMN со сценарием главный — сценарий 3 и экран «Аналитика»
  (они совпадают с кодом). PNG не перерисовывается. *Почему:*
  ветвление и возврат при ошибке на BPMN верные, отличается только порядок шагов; исходника BPMN
  нет, перерисовка дороже пользы.
- **Р-3. Принято / отклонено:** обязательный редактируемый исходник — для диаграмм, созданных или
  доработанных с ИИ (все они в `.puml`). BPMN нарисованы вручную в редакторе — остаются PNG; для
  схемы БД исходником считается DDL. *Отклонено:* восстанавливать mermaid-копии BPMN — они ранее
  удалены как дубли, а две версии одной диаграммы снова разойдутся. Правило в AGENTS.md §7
  уточнено.
- **Р-4. Отклонено для WebLab#1:** правка `ATAP.ConsoleUI/appsettings.json` и `CHECK` роли в DDL.
  *Почему:* по ранее принятому решению расхождения кода в WebLab#1 только документируются
  (см. выше); оба пункта переносятся в WebLab#2/#7 вместе с G-5…G-12.
- **Р-5. Принято:** комплект помечен как **v2.0-rc**; утверждённой v2.0 он становится после ответов
  на Q-1…Q-5 (README, строка версии под оглавлением). *Почему:* без этих ответов нельзя
  проектировать часть API и C4 L2 — объявлять комплект согласованным преждевременно.

  перспективу, а не ошибка описания.
- **Р-10. Уточнено (K-12):** репозитории кэшируют аэропорты под отдельным ключом `airports:all:db`

## WebLab#2 — контракт REST API

Контракт — [`web_lr2/openapi.yaml`](web_lr2/openapi.yaml) (OpenAPI 3.1, пути `/api/v1/…`).

### Взаимодействия, не выражаемые через REST

**Решение:** отдельный контракт (AsyncAPI, SSE, WebSocket, gRPC, webhook) не проектируется.
*Почему:* в требованиях WebLab#1 нет взаимодействия, которое REST не выражает.

| Механизм | Нужен ли | Обоснование |
|---|---|---|
| SSE (поток сервер → клиент) | нет | карта по FR-04 обновляется раз в 5 минут, витрина — пачками; хватает опроса `GET /api/v1/flights/current` с `ETag`/`If-None-Match` (ответ `304`, если снимок не изменился) |
| WebSocket (двусторонний обмен) | нет | чата, совместного редактирования и команд в реальном времени нет |
| gRPC (межсервисный RPC) | нет | сервисов, вызывающих друг друга, нет; OpenSky читает Airflow, а не API |
| Брокер сообщений, webhook | нет | асинхронных интеграций с внешними системами в требованиях нет; загрузка данных — DAG Airflow (FR-17…FR-19) вне границ API |

*Пересмотр:* если появятся уведомления о превышении загруженности или обновление карты чаще
раза в минуту — для потока на клиент использовать SSE (однонаправленный, работает поверх HTTP),
контракт описать в AsyncAPI. SignalR в Blazor — транспорт самого интерфейса, к публичному API
не относится.

### Ревью смысла контракта

Проверены методы HTTP, идемпотентность, коды ответов, обязательные поля, пагинация, ошибки.
Спорные решения сверены с README §6 и с текстами RFC 9110, RFC 9457, RFC 7396 (цитаты ниже
проверены по тексту документов, а не по памяти). Проход сделан дважды: вручную и автоматической
проверкой правил по всем 23 операциям.

**Исправлено в `openapi.yaml`:**

| # | Находка | Решение | Основание |
|---|---|---|---|
| 1 | `404` при неизвестном `airportId` в запросе витрины и в теле `createReport`: ресурс по адресу существует (коллекция отчётов, витрина), неверно значение поля | `400` с типом `unknown-airport`; `404` остался только у `getAirport` | RFC 9110 §15.5.5: `404` — сервер «не нашёл актуальное представление *целевого ресурса*»; здесь целевой ресурс (коллекция отчётов, витрина) есть, ошибочно значение поля |
| 2 | период назван `from`/`to` в запросе и `dateFrom`/`dateTo` в отчёте | везде `dateFrom`/`dateTo` — как в README и DDL; параметры отчёта подставляются в запрос без переименования | единообразие имён |
| 3 | в ответе витрины `total` и `summary.total` — одно и то же число | оставлен `total` (из `PageMeta`), `summary.total` убран | избыточность, риск расхождения |
| 4 | `401` при неверном пароле без заголовка `WWW-Authenticate` | заголовок добавлен | RFC 9110 §15.5.2: «The server generating a 401 response MUST send a WWW-Authenticate header field» |

**Проверено, оставлено без изменений:**

| Решение | Вывод |
|---|---|
| Идемпотентность: `GET`, `PUT`, `DELETE` идемпотентны; повторный `DELETE` даёт `404`, повторный выход — `401` | соответствует RFC 9110 §9.2.2 (идемпотентность — про состояние, а не про код ответа); описано в операциях |
| `POST` (`createUser`, `createReport`, `createSession`) неидемпотентны, ключа идемпотентности нет | повтор `createUser` безопасен — даёт `409`; повтор `createReport` создаст дубль — допустимо, имя не уникально |
| `PATCH` в `application/merge-patch+json`, пустой объект — `400` | схема `UserPatch` запрещает `null` и пустое тело |
| Пагинация `limit`/`offset`, `total` в ответе | достаточна для объёма данных; для треков (`listFlightPositions`) при росте данных потребуется курсорная |
| `listCurrentFlights` без пагинации, `listAirports` с `limit` до 10000 | карте нужен весь снимок и весь справочник (проверено по `MapViewModel`, `AnalyticsViewModel`) |
| `listCurrentFlights`: ограничение выдачи видимой областью | **Решение автора: добавить только `bbox`** (необязательный параметр, FR-06 в части видимой области). Заложено на рост числа судов; существующий клиент без параметра получает весь снимок. Фильтры по высоте и стране (остальное в FR-06) не добавлены: на карте их нет |
| Доступ гостя к судам, рейсам и трекам | **Решение автора: справочник судов (`listAircraft`, `getAircraft`), рейсы (`listFlights`, `getFlight`) и треки (`listFlightPositions`) — только `analyst` и `admin`.** Гость по README видит карту: маркеры судов (`listCurrentFlights`) и аэропорты (`listAirports`) остаются публичными. Закрыты и списки рейсов, чтобы не было «трек закрыт, а рейс открыт» |
| Обязательные поля `CongestionEntry` и `Position`, хотя столбцы в DDL допускают `NULL` | данные заполняет ETL, пустых значений в рабочих данных нет; при их появлении схему ослабить |
| Регистрация и добавление администратором — один запрос `POST /api/v1/users` | **Решение автора: оставить один.** Создаётся один и тот же объект «пользователь»; различается только право указывать `role` (гость → роль `analyst`, при попытке указать `role` — `403`) |
| `Location` в ответе `201` на `createUser` | **Решение автора: возвращать только администратору.** Ссылка ведёт на `getUser`, доступный только `admin`; гость (не вошедший) не вправе читать записи пользователей, поэтому при регистрации заголовка нет, данные приходят в теле. RFC 9110 §15.3.2 не требует `Location`: без него созданный ресурс определяется адресом запроса, а тело `201` его описывает |

**Не относится к контракту, передано в WebLab#3:** CORS и ответы на `OPTIONS` для SPA с другого
адреса, ограничение частоты попыток входа (`429`), условные запросы `ETag` для остальных `GET`.

**Автоматическая проверка правил по 23 операциям** (скрипт разбирает `openapi.yaml`): `POST` →
`201` + `Location`; `DELETE` → `204`; операции с телом → `400` и `415`; ресурс по id → `404`;
закрытые операции → `401` и `403`; каждый `401` содержит `WWW-Authenticate`; списки имеют `limit`
и `offset`; ответы `text/csv` → `406`; у каждого запроса и ответа есть пример. Замечаний нет.
Используются коды: 200, 201, 204, 304, 400, 401, 403, 404, 406, 409, 415, 503.

**Сверка спорных решений с документацией:**

| Вопрос | Что сказано в документе | Решение |
|---|---|---|
| Идемпотентность | RFC 9110 §9.2.2: «PUT, DELETE, and safe request methods are idempotent»; `PATCH` и `POST` в списке нет; идемпотентность — про «intended effect on the server», ответ может отличаться («though the response might differ») | повторный `DELETE` → `404` допустим; `POST` повторять автоматически нельзя («SHOULD NOT automatically retry»), поэтому у `createReport` повтор создаёт дубль осознанно |
| `404` для чужого отчёта | §15.5.5: сервер «is not willing to disclose that one exists»; §15.5.4: сервер, желающий скрыть существование ресурса, «MAY instead respond with 404» | оставлено: чужой отчёт отдаётся как несуществующий |
| Удаление `admin` и себя: `409` или `403` | §15.5.10: `409` — конфликт «with the current state of the target resource», который пользователь «might be able to resolve»; §15.5.4: `403` — сервер «understood the request but refuses to fulfill it» | **Решение автора: `403`.** FR-16 запрещает удалять `admin` безусловно; удалять может только `admin`, поэтому «удалить себя» — частный случай того же запрета. Изначально было `409` (запрет снимался понижением роли), заменено: правило абсолютное, а не зависящее от состояния |
| Неверная ссылка на аэропорт в теле: `400` или `422` | §15.5.21: `422` — синтаксис верный, но сервер «unable to process the contained instructions» | оставлено `400`: во всём контракте ошибки данных — `400`, различать `400` и `422` клиенту незачем; `422` — допустимая альтернатива |
| Расширение `errors` в `Problem` | RFC 9457 §3.2: «Problem type definitions MAY extend the problem details object with additional members»; `status` — «only advisory» (§3.1.2); `type` без значения — `about:blank` (§3.1.1) | расширение допустимо; `type` во всех ошибках задан |
| `null` в `PATCH` | RFC 7396 §1–2: `null` в патче «removes» поле; не-объект заменяет цель целиком | схема `UserPatch` запрещает `null` и пустой объект, обязательные поля удалить нельзя |

### Автоматическая проверка контракта

Контракт проверяется тремя способами; одна команда — `make api-check` (нужен Node.js 18+, пакеты
скачиваются через `npx` с зафиксированными версиями).

| Что | Чем | Файл | Результат |
|---|---|---|---|
| Структура контракта, `operationId`, ссылки, неиспользуемые компоненты | Redocly CLI 1.25.0, `make api-lint` | `web_lr2/redocly.yaml` | 0 ошибок, 0 замечаний |
| Примеры запросов, ответов и параметров по схемам | те же правила Redocly: `no-invalid-media-type-examples`, `no-invalid-parameter-examples`, `no-invalid-schema-examples` (уровень `error`) | `web_lr2/redocly.yaml` | пройдено |
| Многошаговые сценарии на mock-сервере | Prism 5.16.0 с флагом `--errors`, `make api-scenario` | `web_lr2/mock-scenario.mjs` | 30 шагов, все пройдены |

**Проверка самой проверки.** Копия контракта с тремя подложенными ошибками в примерах (роль вне
перечня, отсутствующее обязательное поле `password`, `id` строкой вместо числа) дала три ошибки
линтера, то есть проверка примеров по схемам срабатывает.

**Сценарии на mock-сервере.**

1. *Анализ загруженности* (README §6, сценарий 3): вход → список аэропортов → витрина без токена (`401`)
   → витрина JSON (вылетов + прилётов = записей) → витрина CSV (`Accept: text/csv`) → сохранение отчёта
   (пустое имя — `400`, документированный `400` Problem Details) → список отчётов → повторная выгрузка
   → удаление (`204`) → удалённый отчёт (`404`) → выход (`204`).
2. *Администрирование пользователей* (CRUD и частичное обновление): вход админом → список → создание
   (`201`, повтор логина — `409`) → чтение одного → `PUT` целиком → `PUT` без обязательных полей (`400`)
   → `PATCH` только роли (`200`) → `PATCH` пустым объектом и с `null` (`400`) → `PATCH` с неверным
   `Content-Type` (`415`) → удаление админа (`403`) → удаление (`204`).

**Что такая проверка не доказывает.** Prism отдаёт готовые примеры и состояния не хранит:
идемпотентность, права по ролям и бизнес-правила (период до 31 дня, уникальность логина) он не
проверяет. Они проверяются на реальном сервере в WebLab#3, тем же скриптом через `MOCK_URL`.
Ответы Prism на нарушение схемы (`400`, перечень в заголовке `sl-violations`) совпадают с кодом
`400`, описанным в контракте.

### Управление изменением: контракт 1.0.0 → 1.1.0

**Найдено при проверке схем:** пароль при создании пользователя и при смене через `PATCH`
допускал 1 символ и не имел верхней границы (`minLength: 1`). В README и ADR-0004 требований к
длине нет — решение принято автором.

**Решение автора:** длина пароля 8–128 символов (только длина, без требований к составу).
Нижняя граница отсекает слишком короткие пароли, верхняя защищает хэширование (PBKDF2) от
чрезмерно длинных значений. На вход (`createSession`) ограничение не распространяется, чтобы не
отсекать уже существующие пароли: при входе сверяется хэш.

**Что изменено** (полная разница — [`web_lr2/versions/1.0.0-to-1.1.0.diff`](web_lr2/versions/1.0.0-to-1.1.0.diff),
исходная версия — `web_lr2/versions/openapi-1.0.0.yaml`):

| Место | Изменение |
|---|---|
| `info.version` | 1.0.0 → 1.1.0 |
| схемы `UserCreate`, `UserPatch`, поле `password` | `minLength: 1` → `minLength: 8`, добавлен `maxLength: 128` |
| ответ `ValidationError` (`400`) | один пример → два; добавлен `weakPassword` с `errors[{field: password}]` |
| `scenarios.md` | коды `400` в шагах регистрации, «Добавить» и `PATCH` дополнены; добавлен раздел об уточнении |
| `README.md` §6, `AGENTS.md` §7 | критерий приёмки сценария 1 и бизнес-правило о длине пароля |
| `web_lr2/mock-scenario.mjs` | четыре новых шага: пароль из 3 символов, из 129 символов, слабый пароль (документированная ошибка), `PATCH` с коротким паролем |

**Проверка после изменения:** `make api-check` — линтер без замечаний, примеры соответствуют
схемам (в том числе пароли в примерах: 9, 11 и 12 символов), 30 шагов сценариев пройдены. Diff
состоит только из задуманных изменений: версия, диапазон длины в двух схемах, пример ошибки.

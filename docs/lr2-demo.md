# Демонстрация ЛР №2 по тестированию

План показа на 10–15 минут. Это работа про интеграционные тесты, E2E, Docker, Jenkins и отчётность.
OpenAPI, Swagger и Prism не являются основной демонстрацией этой лабораторной.

## Подготовка до защиты

Нужны Docker Desktop, .NET SDK 8, Git Bash; Make — для коротких команд.
Allure на хост отдельно устанавливать не нужно: при показе CI отчёт строится внутри Jenkins.

Открыть Docker Desktop. В VS Code выбрать терминал **Git Bash**:

```bash
cd /c/ATAP
bash ci/jenkins.sh up
```

Открыть http://localhost:8085/job/atap-tests/.
Оставить две вкладки: задание Jenkins и проверенную сборку №8:
http://localhost:8085/job/atap-tests/8/.

Отчёт сборки №8:
http://localhost:8085/job/atap-tests/8/artifact/ci-results/allure-report/index.html

Подготовить файлы VS Code:

- `docker-compose.test.yml`;
- `ci/Dockerfile.tests`;
- `ci/run-tests.sh`;
- `Jenkinsfile`;
- `ci/finish.sh`;
- `ATAP.IntegrationTests/Infrastructure/TestDatabaseFixture.cs`;
- `ATAP.IntegrationTests/Infrastructure/TestRedisFixture.cs`;
- `ATAP.IntegrationTests/BusinessLogic/AdminService_DeleteUser_AdminUser_Throws_IntegrationTest.cs`;
- `ATAP.IntegrationTests/DataAccess/UserRepository_Create_PersistsUser_IntegrationTest.cs`;
- `ATAP.E2ETests/DemoScenario_AnalystAnalyzesCongestionAndSavesReport_E2ETest.cs`;
- `scripts/e2e-curl.sh`, `scripts/capture-traffic.sh`;
- `docs/traffic/e2e-traffic.log`.

Jenkins получает код из локального Git, ветки main. Он тестирует коммит, а не несохранённые или
незакоммиченные изменения рабочей папки. Локальный `make test` использует рабочую папку.

## 1. Начать с результата и запустить CI

Сказать:

> В рамках работы я подготовила отдельный тестовый стенд, интеграционные тесты репозиториев
> и сервисов, E2E-сценарий по HTTP и запуск всех уровней тестов в Jenkins.
> Дополнительно настроены отчёт Allure с историей, очистка окружения и захват HTTP-трафика.

Запустить:

```bash
bash ci/jenkins.sh build
```

Открыть новую сборку в Jenkins и Console Output. Пока она выполняется, показывать следующие файлы.
Не запускать одновременно вторую сборку кнопкой: достаточно одного способа запуска.
Время зависит от кэша образов и доступности NuGet; первую сборку лучше сделать до защиты.

## 2. Тестовый стенд — основная задача 1

Показать `docker-compose.test.yml`.

Сказать:

> Стенд содержит PostgreSQL с PostGIS, Redis и тестируемый API.
> Разовый контейнер db-e2e создаёт отдельную базу для E2E из подготовленного шаблона.
> У стенда своё имя проекта и свободные порты, рабочая база приложения не используется.

Показать `db/test/Dockerfile` и `db/test/03_seed_test_data.sql`.

> При создании стенда выполняются DDL и фиксированный набор тестовых данных.
> Поэтому можно проверять точные результаты: например, за выбранные сутки 4 записи,
> из них 1 вылет и 3 прилёта. Позиции для карты привязаны ко времени создания стенда.

## 3. Контейнер тестов и порядок CI — основная задача 4

Показать `ci/Dockerfile.tests`, затем `ci/run-tests.sh` и `Jenkinsfile`.

> Тесты выполняются в отдельном контейнере с .NET SDK. Зависимости NuGet устанавливаются при
> сборке образа. При запуске контейнер клонирует репозиторий, выбирает коммит, собирает тесты
> и выполняет этап. Jenkins задаёт порядок: Unit, затем Integration, затем E2E.

Пояснить различие:

- `ci/jenkins.sh` управляет локальным Jenkins и запускает сборку;
- `Jenkinsfile` определяет этапы;
- `ci/run-tests.sh` выполняется внутри контейнера тестов.

## 4. Интеграционные тесты — основная задача 2

Показать тест `UserRepository_Create_PersistsUser_IntegrationTest.cs`.

> Это проверка реального репозитория с PostgreSQL: создаём пользователя и проверяем сохранение.
> Вместо БД здесь нет mock-объекта.

Затем `AdminService_DeleteUser_AdminUser_Throws_IntegrationTest.cs`:

> Здесь проверяется бизнес-логика вместе с репозиторием и БД. Пытаемся удалить администратора,
> ожидаем конкретное исключение и проверяем SQL-запросами, что пользователи и отчёты не изменились.

Показать Arrange, Act, Assert. В интеграционных тестах один файл содержит один тест;
подготовка вынесена также в фикстуры. Фактически integration — 41 тест.

## 5. Изоляция, повторяемость и параллельность

Показать `TestDatabaseFixture.cs`:

> Каждый тестовый класс получает копию базы-шаблона с уникальным именем.
> Копирование защищено блокировками. После теста копия удаляется.

Показать `TestRedisFixture.cs`:

> У каждого класса свой префикс Redis-ключей; после выполнения эти ключи удаляются.
> Поэтому параллельные тесты не используют чужие данные.

Показать результаты проверки от 06.11.2026:

- `TestResults/lr2-audit/sequential-1.log` и `sequential-2.log` — оба 41/41;
- `TestResults/lr2-audit/parallel-1.log` и `parallel-2.log` — оба 41/41;
- `remaining-test-databases.txt` и `remaining-test-redis-keys.txt` — пустые.

Если нужно повторить именно эту проверку на том же рабочем месте, после сборки тестов:

```bash
bash scripts/test-stand.sh with bash TestResults/lr2-audit/repeat-integration.sh
```

Это локальный вспомогательный скрипт аудита, не часть закоммиченного проекта.
Для обычного самостоятельного запуска интеграционных тестов используется `make test-integration`.

## 6. E2E — основная задача 3

Открыть `DemoScenario_AnalystAnalyzesCongestionAndSavesReport_E2ETest.cs`.

> E2E работает с запущенным приложением только через HTTP.
> Сценарий: гость смотрит карту, получает отказ в аналитике, входит как аналитик,
> получает JSON и CSV, сохраняет отчёт, читает его, удаляет и выходит.
> В конце проверяется, что токен после выхода не принимается.
> Запросы проходят через настоящий API, сервисы и хранилище; GUI не участвует.

Показать несколько проверок:

- 3 рейса в снимке карты и условный запрос 304;
- в аналитике 4 записи, 1 вылет и 3 прилёта;
- число строк CSV;
- 201 и Location созданного отчёта;
- 404 после удаления;
- 401 после выхода.

## 7. Отчёт, история и завершение сборки

Вернуться в Jenkins. Успешная проверенная сборка №8 содержит:

- Unit: 76 + 12 + 15 = 103;
- Integration: 41;
- E2E: 1;
- всего Allure: 145 пройдено, без ошибок и пропусков.

В новой сборке ожидается тот же набор, если код тестов не изменялся.

Открыть **Artifacts → ci-results → allure-report → index.html**.
Показать Overview, список тестов и график истории. В отчёте №8 есть 7 точек тренда.

> Результаты записываются в Allure и TRX. История хранится отдельно и добавляется к следующему
> отчёту, поэтому можно сравнивать прогоны. Отчёт доступен как артефакт сборки.

## 8. Что происходит после сбоя и как очищается стенд

Показать `Jenkinsfile`: `post { always }`, затем `ci/finish.sh`.

> Если этап падает, последующие этапы не выполняются. Завершающий блок всё равно помечает
> неисполненные этапы как skipped, формирует отчёт и удаляет стенд с данными.
> История отчётов сохраняется отдельно от временных данных сборки.

Открыть сохранённую сборку №4:
http://localhost:8085/job/atap-tests/4/

В Console Output найти `E2E skipped`, `Report successfully generated` и удаление стенда.
В её Allure: 97 passed, 1 skipped.

Обязательно уточнить:

> Это сохранённая проверка механизма остановки конвейера с прежней имитацией ошибки.
> Сейчас параметр имитации удалён; это не новый запуск с настоящим падением теста.

При отдельном требовании показать реальное падение текущего теста нужна самостоятельная
демонстрация в изолированной копии репозитория. Не менять основной коммит и не удалять историю
Jenkins ради показа. Сборка №4 не подменяет такую демонстрацию.

Показать в успешной сборке строки удаления контейнеров. Для №8 можно проверить:

```bash
docker ps -a --filter label=com.docker.compose.project=atap-ci-8
docker volume ls --filter name=atap-ci-results-8 --filter name=atap-ci-work-8
```

Строк контейнеров и временных томов этой сборки быть не должно. Сам Jenkins остаётся работать.
При аварийном завершении тестов уничтожается и тестовый API с его состоянием токенов.

## 9. Запросы и захват трафика — основная задача 5

Запустить во втором терминале Git Bash:

```bash
bash scripts/capture-traffic.sh
```

> Скрипт поднимает отдельный стенд и mitmproxy перед API.
> Curl выполняет основной пользовательский сценарий через прокси;
> mitmproxy записывает запросы и ответы. В конце прокси и стенд удаляются.

Ожидается сообщение о 15 запросах с совпавшими кодами.
Открыть `docs/traffic/e2e-traffic.log` и показать:

- метод и адрес запроса;
- код ответа и Content-Type;
- JSON или CSV;
- 201 с Location, 204, 401 после выхода.

`docs/traffic/e2e.flow` — машинный дамп для mitmproxy; текстовый `.log` удобен для VS Code.
Актуальный повторный захват аудита также сохранён в `TestResults/lr2-audit/traffic-current/`.

Оговорка: curl содержит 15 запросов основного пути, текущий E2E расширен дополнительными
проверками. Нельзя называть их полностью одинаковыми наборами запросов.

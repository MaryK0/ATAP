# ЛР2 по тестированию — план показа в Jenkins

Все команды — в **Git Bash**. Нужны Docker Desktop с Linux-контейнерами,
Git и Wireshark. Тесты и Allure запускаются в Docker; пять рабочих копий
проекта и Allure на хосте для этого плана не нужны.

## 0. Подготовить до защиты

```bash
cd /c/ATAP
bash ci/jenkins.sh up
```

Открыть http://localhost:8085/job/atap-tests/.
Настройка по умолчанию — пять executors, задаётся JENKINS_EXECUTORS в
ci/docker-compose.jenkins.yml и init-скриптом executors.groovy.
Проверить: Manage Jenkins → Nodes → Built-In Node → Configure → Number of executors = 5.

Если нужно показать код на GitHub, отправить готовые коммиты:

```bash
git push origin main
```

Незакоммиченные изменения эта команда не добавляет.

## 3. Пять обычных сборок одновременно

В присланных девяти требованиях числа «пять» нет. Это дополнительный показ,
использующий обычную возможность Jenkins запускать независимые сборки.
Специальных параметров, веток “пять разработчиков” и особых тестов нет.

Нажать Build Now и убедиться, что в истории появился **новый работающий номер**.
Не дожидаясь завершения, повторить ещё четыре раза. Нужны пять разных номеров,
а не пять быстрых кликов, которые Jenkins может объединить в один запрос очереди.

Командный вариант: открыть пять терминалов Git Bash. В каждом выполнить:

```bash
cd /c/ATAP
bash ci/jenkins.sh build
```

Следующий терминал запускать после появления `Build #N` в предыдущем,
но **до завершения** предыдущей сборки. Команда каждого терминала ждёт
только свою сборку и в конце выводит ссылку на её Allure.

Показать пять активных сборок и занятых executors в Jenkins.
В Docker Desktop показать группы atap-ci-N с разными N.
У каждой сборки собственные теги образов, контейнеры, сеть, БД, порты и результаты.
Во всех пяти обычный unit → integration → E2E. Дождаться SUCCESS у каждой.

Открыть Allure каждой сборки: ожидается 152/152 в каждом из пяти отчётов.
Всего выполнено 5 × 152 = 760 тестов; это пять отчётов, а не один отчёт на 760.
История Allure обновляется под файловой блокировкой, поэтому записи сборок
не перезаписывают друг друга. В новых точках тренда есть номера и ссылки.

**Сказать:** «Это пять полных независимых сборок одного задания, например
запуски пяти разработчиков. Тестовые данные изолированы. Общий кэш образа
и история отчётов обновляются под блокировками, сами тесты идут параллельно».

## 4. Вручную остановить PostgreSQL

Открыть успешную сборку текущего Jenkinsfile → Replay.
В Main Script внутри steps этапа Integration перед sh временно добавить:

```groovy
input message: 'Остановите postgres-test этой сборки вручную, затем Proceed'
```

Нажать Run. После unit и готовности стенда Jenkins будет ждать подтверждения.
Узнать **новый** номер N. В Docker Desktop в группе atap-ci-N нажать Stop
у postgres-test. Либо вручную выполнить из корня проекта с реальным N:

```bash
docker compose -p atap-ci-N -f docker-compose.test.yml stop postgres-test
```

Вернуться в Jenkins → **Proceed**, не Abort. Дождаться FAILURE и открыть
Allure этой сборки. Проверки PostgreSQL получат ошибки, E2E — skipped.
Redis-тесты могут пройти: Redis не остановлен. Ранее было 112 passed,
39 broken и 1 skipped. Это не изменение ожидаемых результатов тестов.

**Сказать:** «Я вручную остановила БД. Integration обнаружил недоступность,
E2E не запустился, но отчёт сформирован и тестовый стенд очищен».

Replay/input — штатные средства Jenkins. Временная пауза существует только
в этой повторной сборке, Jenkinsfile репозитория не меняется.

## 5. Вручную остановить API

Снова Replay исходной успешной обычной сборки, без предыдущей вставки.
Добавить input **перед sh в этапе E2E** и нажать Run.
После успешных unit/integration остановить atap-api группы новой сборки N:

```bash
docker compose -p atap-ci-N -f docker-compose.test.yml stop atap-api
```

Нажать Proceed. Ожидается FAILURE: E2E получает ошибку HTTP, Allure сохраняется.
Ранее результат был 151 passed и 1 broken.

**Сказать:** «Теперь недоступен API. Реальный HTTP E2E обнаруживает отказ,
при этом отчёт и очистка выполняются».

Не нажимать новый Build Now для проверки остановленного стенда: он создаст
новое окружение. Именно Proceed продолжает тесты на уже поднятом стенде.
Рабочие БД и WebLab#4 не останавливать.

## 6. Снова пять сборок: логи и HTTP в Wireshark

Чтобы успеть показать HTTP до автоматической очистки, использовать временную
паузу Replay после успешного E2E. В исходной успешной сборке открыть Replay
и внутри steps этапа E2E **после sh** добавить:

```groovy
input message: 'Тесты завершены. Покажите HTTP в Wireshark, затем Proceed для отчёта и очистки'
```

Открыть пять вкладок Replay одной исходной сборки, вставить эту строку и
нажать Run в каждой. Убедиться в пяти разных работающих номерах.
Это пять полных обычных конвейеров с временной операторской паузой.
После E2E стенды остаются живыми до нажатия Proceed.

В консоли каждой сборки найти `[build]` и `[stand]`:

```text
[build] number=N commit=... project=atap-ci-N image=atap-tests:ci-N
[stand] build=N project=atap-ci-N api=http://127.0.0.1:ПОРТ
```

Здесь настоящие номер, коммит, Compose-проект и API-порт конкретного прогона.
Не использовать порты старых завершённых сборок. Идентичность разработчика
не подделывается: показывается сборка, её инициатор и соответствующий стенд.

В Wireshark выбрать **Adapter for loopback traffic capture / Npcap Loopback Adapter**
и начать запись. Для каждого из пяти реальных адресов отправить гостевой запрос:

```bash
curl -i 'http://127.0.0.1:ПОРТ/api/v1/airports?limit=1'
```

ПОРТ заменить значением из `[stand]` своей сборки. Получить 200 OK.
Остановить запись. Если протокол не распознан: выделить TCP-пакет нужного порта →
Analyze → Decode As → TCP port: этот порт → HTTP. Повторить для остальных портов.
Фильтр `http.request`. Для отдельного прогона добавить `&& tcp.port == ПОРТ`.

Показать GET, Host и TCP-порт, сопоставить с `[stand]` и группой Docker.
**Сказать:** «По номеру сборки и порту видно, к какому независимому стенду
относится запрос. Здесь настоящий HTTP, записанный Wireshark».

Сохранить через File → Save As в `C:\ATAP\TestResults\lr2\developers.pcapng`.
Затем в каждой из пяти сборок нажать **Proceed**: сформируется Allure,
обновится общая история и удалятся только её контейнеры и временные данные.
Адрес API сохранится в артефакте ci-results/stand.txt, но после очистки уже не работает.

## 7. Пункт 5 задания: полный curl-сценарий и mitmproxy

```bash
cd /c/ATAP
bash scripts/capture-traffic.sh
```

Показать 27 запросов, ожидаемые и полученные коды.
Открыть TestResults/lr2/traffic/e2e-traffic.log.
Для просмотра flow через браузер:

```bash
MSYS_NO_PATHCONV=1 docker run --rm \
  -p 127.0.0.1:8089:8081 \
  --mount type=bind,source=C:/ATAP/TestResults/lr2/traffic,target=/capture,readonly \
  mitmproxy/mitmproxy:10.4.2 \
  mitmweb --web-host 0.0.0.0 --web-port 8081 \
  --set web_open_browser=false -r /capture/e2e.flow
```

Открыть http://localhost:8089/. Ctrl+C остановит просмотр.
**Сказать:** «Curl воспроизводит HTTP-действия E2E, mitmproxy записывает
трафик. В сохранённой копии скрыты пароли и JWT. E2E дополнительно проверяет
тела, заголовки и конкретные значения данных».

## 8. Завершение

```bash
cd /c/ATAP
bash ci/jenkins.sh build
```

Показать обычный SUCCESS после отказов. В нём нет временных пауз Replay.
После защиты Jenkins можно остановить с сохранением истории:

```bash
bash ci/jenkins.sh down
```

Само задание требует отдельный стенд, integration/E2E, контейнер тестов,
CI, пропуски после ошибки, Allure с трендом и захват HTTP. Число пять и
ручные остановки относятся к дополнительному сценарию показа.

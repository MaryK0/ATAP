# ЛР2 по тестированию: задание и ручная демонстрация

## Что реализовано по заданию

| Пункт | Реализация |
|---|---|
| Тестовое окружение на машине студента | `docker-compose.test.yml`, `scripts/test-stand.sh`: PostgreSQL/PostGIS, Redis, API; отдельные имена и порты |
| Integration доступа к данным и бизнес-логики | `ATAP.IntegrationTests/`: реальные PostgreSQL и Redis |
| E2E демонстрационного сценария | `ATAP.E2ETests/`: HTTP API, карта → вход → аналитика → отчёт → выход |
| Старые и новые тесты в CI | `Jenkinsfile`, `ci/Dockerfile.tests`, `ci/run-tests.sh` |
| Запросы и захват трафика | `scripts/e2e-curl.sh` (27 запросов), `scripts/capture-traffic.sh` (mitmproxy) |
| Отдельный контейнер тестов и получение кода | .NET SDK и зависимости в образе; clone и checkout коммита внутри контейнера |
| Отдельное воспроизводимое хранилище | `db/test/Dockerfile`, DDL и фиксированный seed; БД-копии для integration, отдельная atap_e2e для API |
| unit → integration → e2e | Последовательные этапы Jenkins, без специальных демонстрационных веток |
| Использование именно этого стенда | `ci/lib.sh` передаёт ATAP_TEST_PG, ATAP_TEST_REDIS, ATAP_TEST_API |
| Мобильное устройство | Не применяется: ATAP — веб-приложение |
| Ошибка останавливает следующие этапы, отчёт сохраняется | Jenkins + `post always`, `ci/finish.sh`, результаты skipped |
| Тренды между запусками | Allure history хранится в постоянном томе Jenkins |

## Обычный запуск

Нужны Docker Desktop с Linux-контейнерами и Git Bash. В корне проекта:

```bash
bash ci/jenkins.sh up
bash ci/jenkins.sh build
```

Либо открыть http://localhost:8085/job/atap-tests/ и нажать **Build Now**.
После первого запуска обновлённого Jenkinsfile старые параметры задания
должны исчезнуть. В текущем Jenkinsfile нет параметров выбора отказа или
режима пяти разработчиков.

Ожидаемый порядок: образ тестов → unit → запуск стенда → integration → E2E.
Образ и стенд — подготовительные этапы; уровни тестирования идут в требуемом порядке.

Jenkins клонирует закоммиченный код. Незакоммиченные изменения рабочей папки
не входят в проверяемый коммит. Результаты обычного проверенного набора:
109 unit + 42 integration + 1 E2E = 152 теста.

На странице сборки открыть Artifacts → ci-results → allure-report → index.html.
В Overview показать статистику и Trend. В репозитории показать Jenkinsfile
(Groovy), docker-compose.test.yml (YAML), ci/Dockerfile.tests и один тест каждого уровня.

## Воспроизведение E2E и запись HTTP — пункт 5 задания

```bash
bash scripts/capture-traffic.sh
```

Команда поднимает отдельный стенд, запускает mitmproxy перед API и выполняет
27 запросов curl. Проверяются коды ответов. Сам E2E дополнительно проверяет
заголовки, тела и значения данных. Журнал и flow сохраняются в
`TestResults/lr2/traffic/`; пароли и JWT скрываются только в сохраняемой копии.
Стенд и прокси удаляются после выполнения, включая ошибку.

Для просмотра flow использовать `mitmproxy -r <путь>` или `mitmweb -r <путь>`.
Ранее сохранённые `docs/traffic/` — исторические записи.

## Дополнительный ручной показ отказа — отдельно от штатного CI

Пункт 8 требует пропуск следующих этапов и отчёт после ошибки. Он не требует
флага остановки БД. Если преподаватель просит остановить контейнер, это
делает оператор вручную. В репозитории нет скрипта, который вызывает такой отказ.

Чтобы успеть остановить нужный контейнер, можно использовать стандартный
Jenkins **Replay** и временный шаг **input**. Изменение существует только в
этой повторной сборке и не добавляется в Jenkinsfile репозитория.

### PostgreSQL

1. Открыть завершённую обычную сборку → Replay.
2. В поле Main Script найти этап Integration. Перед его `sh` временно добавить:

   ```groovy
   input message: 'Стенд готов. Остановите тестовую PostgreSQL вручную, затем нажмите Proceed'
   ```

3. Нажать Run. После unit и запуска стенда Jenkins остановится на ожидании.
4. В Docker Desktop найти группу `atap-ci-N` **новой** сборки и нажать Stop
   у `postgres-test`. Не трогать рабочую БД или контейнеры WebLab#4.
5. Вернуться в Jenkins и нажать **Proceed**, не Abort.
6. Убедиться: integration получает ошибки подключения, E2E skipped,
   сборка FAILURE, Allure создан. Тестовый стенд удаляется после завершения.

При работающем Redis его отдельные тесты могут пройти. Это ожидаемо:
отказ PostgreSQL не должен превращать все независимые проверки в ошибки.

### API

1. Снова Replay исходной обычной сборки, без предыдущей временной вставки.
2. Добавить `input` перед `sh` в этапе E2E.
3. После успешного integration вручную остановить `atap-api` группы этой сборки.
4. Нажать Proceed: E2E получает ошибку HTTP, отчёт формируется.

Новый обычный Build Now снова использует исходный Jenkinsfile без пауз.
Этот показ не требует изменения ожидаемых результатов тестов.

## Дополнительная просьба о пяти параллельных запусках

В присланных пяти задачах и девяти требованиях числа «пять» нет.
Специального режима или параметра в Jenkinsfile для него нет.

Если такой показ нужен отдельно, используются обычные инструменты проекта:
пять локальных Git-копий одного коммита и пять терминалов. В каждой копии
запускается существующий `make test`. Имя Compose-проекта и порты выделяются
автоматически; БД-копии и Redis-префиксы тестов уникальны. Отдельные рабочие
папки разделяют bin/obj и Allure-результаты. Каждый запуск выполняет обычный
unit → integration → E2E, а не специально изменённый набор тестов.

Имена проектов и адреса видны в выводе `test-stand.sh` и в Docker Desktop.
Для ручного показа HTTP поднять стенды командой `bash scripts/test-stand.sh up`,
сохранить выведенные адреса, запустить Wireshark на loopback и вручную выполнить
curl к API-порту каждого стенда. Сопоставление — по TCP-порту и имени проекта.
Не запускать `make test` для уже остановленного стенда: эта команда создаёт
новое окружение. Чтобы проверить существующий стенд, нужны выведенные
ATAP_TEST_* и обычный `dotnet test` соответствующего проекта.

Обычные Jenkins-сборки остаются последовательными для общей истории Allure.
Ручной многопользовательский показ не является частью штатного CI.
